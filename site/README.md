# Каркас сайта ФТСО (ftso67.ru)

Официальный сайт Федерации тенниса Смоленской области. Это **шаг 2**: рабочий
каркас на Node, публичная главная по утверждённому дизайну и первый живой
раздел — рейтинг — сквозным срезом (админ вводит → пересчёт → витрина).

Рейтинговый движок лежит рядом, в `../rating/`, и **подключается как модуль**.
Он не переписывался: каркас только собирает для него вход из SQLite и кладёт
результат в снимок.

## Быстрый старт

```bash
cd site
npm install
cp .env.example .env      # заполнить SESSION_SECRET и SUPER_ADMIN_PASSWORD
npm run migrate           # схема; ОТДЕЛЬНОЙ командой ДО старта сервера
npm run seed              # выдуманные данные + два снимка рейтинга
npm start                 # http://127.0.0.1:3000
```

Приёмка одной командой (поднимает изолированную базу, ничего не трогает в вашей):

```bash
npm run accept
```

## Что внутри

```
site/
  server/     Express: маршруты, middleware (сессия, роли, лимиты, CSRF, лог)
    lib/      пароли, конфиг, CSRF, стор сессий, валидация, сервис рейтинга, меню
    routes/   public, rating, auth, admin
  db/         schema.sql, migrate.mjs, connect.mjs, seed.mjs
  views/      главная (из дизайна), /rating, вход, админ-страницы, ошибки
  public/     статика: css, js, локальные шрифты
  tools/      разовая загрузка шрифтов в самохост
  acceptance.mjs
../rating/    движок (уже был; только подключается)
```

Каркас лежит в каталоге `site/` — рядом с `rating/`, а не в корне репозитория.
Раскладка перенесена из репозитория, где каркас собирался, один в один: движок
подключается относительными путями (`../rating/`, `../../../rating/`), и стоит
поднять `site/` в корень — все эти импорты придётся править. Поэтому `site/` и
`rating/` остаются соседями.

## Структура сайта

12 разделов из договора (Приложение № 1 «Техническое задание», §3) плюс
динамическая страница турнира:

| Раздел | Адрес | Состояние |
|---|---|---|
| Главная | `/` | по утверждённому дизайну |
| О Федерации | `/federation` | заглушка |
| Новости | `/news` | заглушка |
| Турниры | `/tournaments` | заглушка |
| Страница турнира | `/tournaments/:id` | маршрут-заглушка, 404 на неизвестный id |
| Рейтинг | `/rating` | **живой** |
| Тренеры | `/coaches` | заглушка |
| Теннисные корты | `/courts` | заглушка |
| Теннисные клубы | `/clubs` | заглушка |
| Судьи | `/referees` | заглушка |
| Галерея | `/gallery` | заглушка |
| Документы | `/documents` | заглушка |
| Контакты | `/contacts` | заглушка |

Заглушки — публичные, отдают HTTP 200 с корректным `<title>` (иначе поисковик не
проиндексирует адрес). Плюс правовые страницы `/privacy` и `/consent` (152-ФЗ) —
они настоящие, ссылки в подвале ведут на них.

**Меню шапки.** В макете пункты были якорями одной страницы, а сайт
многостраничный, поэтому ссылки перестроены на реальные разделы. Все 12 полных
названий в один ряд не помещаются (контейнер макета — 1200px), поэтому шесть
основных стоят пилюлями, как в дизайне, а остальные шесть — под кнопкой «Ещё».
На узком экране всё меню уходит в бургер плоским списком.

## Рейтинг: как работает вертикаль

1. Админ (`super-admin` или `tournament-admin`) ведёт игроков, турниры,
   результаты и (по желанию) матчи для тай-брейка.
2. Кнопка «Пересчитать» собирает `{tournaments, results, matches}` из SQLite,
   зовёт `computeStandings` из `../rating/`, кладёт итог новой строкой в
   `rating_cache`. Пересчёт **по кнопке**, не по расписанию.
3. Колонка «Изменение» (▲/▼/—) считается **на уровне сайта**: сравниваются два
   последних снимка по `player_id`. Движок остаётся снимком и дельту не считает.
   - предыдущего снимка нет вовсе → «—»;
   - игрок есть в новом, но отсутствует в предыдущем → «нов.».
4. `/rating` — полная таблица с поиском по фамилии и фильтрами по возрастной
   группе и полу (§4.4), выгрузка CSV. Главная показывает топ-5 того же снимка.

Хранится 24 последних снимка, старее чистятся при пересчёте.

**Защита от двойного нажатия — две штуки, и обе нужны.** Лок `compute_lock`
закрывает параллельные вызовы, но одного его мало: `better-sqlite3` синхронный и
процесс один, поэтому два запроса обрабатываются последовательно и первый успевает
снять лок до начала второго. Поэтому есть и минимальный интервал между пересчётами
(`RATING_MIN_INTERVAL_SECONDS`, по умолчанию 10 с). Иначе два почти одинаковых
снимка подряд обнулили бы всю колонку «Изменение». Протухший лок (пересчёт упал на
середине) старше `RATING_STALE_LOCK_MINUTES` считается недействительным — кнопка
не залипает навсегда.

Пустой `rating_cache` — не ошибка: главная и `/rating` показывают «рейтинг ещё не
рассчитан».

## Вход, роли, безопасность

- Пароли — только `crypto.scrypt`, N=16384, r=8, p=1, keylen=64, соль 16 байт.
  Колонка `password_hash` самодостаточна: `scrypt$N$r$p$<соль_b64>$<хэш_b64>`.
  Сверка — `timingSafeEqual`. Несуществующий логин всё равно считает scrypt от
  dummy-значения, чтобы время ответа не выдавало наличие аккаунта.
- Ограничение попыток — в SQLite, переживает рестарт. Блокируется **пара
  логин+IP** (5 неудач / 15 мин), не логин глобально — иначе, зная чужой логин,
  можно заблокировать чужой аккаунт. Плюс общий лимит на IP (20 / 15 мин).
- Сессия — `express-session` со своим стором в SQLite. Cookie: `HttpOnly`,
  `SameSite=Lax`, `Secure` по `NODE_ENV`. Секрет — массив (первый подписывает,
  остальные принимают старые cookie), так что секрет можно менять без разлогина
  всех. Logout уничтожает серверную запись; после входа session ID ротируется.
- CSRF — синхронизирующий токен на каждой форме, включая `/login`, проверяется
  на каждом POST.
- Заголовки: CSP настроен вручную (`default-src 'self'`, `img-src 'self' data:`,
  `script-src 'self' 'nonce-…'`, `font-src 'self'`), `X-Frame-Options: DENY`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy`.
- Все изменения данных пишутся в `action_log` (кто, что, когда).
- Роли: рабочие в этом шаге — `super-admin` (всё) и `tournament-admin`
  (турниры/игроки/результаты/рейтинг). `content-manager` и `news-editor` заведены,
  но не подключены: их матрица доступа определится, когда придут их разделы.
  Публичной формы регистрации нет — пользователей заводит `super-admin`.
- Загрузки файлов в каркасе **нет** — придёт вместе с разделами, с проверкой типа
  и размера.

**Смените пароль супер-админа при первом входе** — «Мой аккаунт» → «Смена пароля»
(требуется текущий пароль). `super-admin` может сбросить пароль другого
пользователя без его текущего — это штатный админ-сброс.

## Дизайн

Главная собрана по `Главная_ФТСО.html`: разметка и стили перенесены один в один,
инлайновый `<style>` вынесен в `public/css/site.css`, а инлайновые атрибуты
`style` заменены классами — иначе строгий CSP (`style-src 'self'`) их заблокировал
бы. Инлайновый анти-FOUC скрипт темы оставлен и работает через `nonce`.

- Тёмная тема с сохранением выбора в `localStorage` (`ftso-theme`) — сохранена,
  включая «волну» перехода сверху вниз.
- Адаптив по `Мобильная_версия.html`: бургер, одна колонка, таблицы с
  горизонтальным скроллом, тяжёлые эффекты приглушены.
- Шрифты Manrope и Inter — **самохост**: `npm run fonts` один раз скачал woff2 в
  `public/fonts` и сгенерировал `public/css/fonts.css` с `font-display: swap`.
  Обращений к `fonts.googleapis.com` / `fonts.gstatic.com` в рантайме нет.
- Блоки «Турниры» и «Новости» на главной — пока статичное содержимое дизайна
  (`server/lib/home-content.mjs`); оживут вместе со своими модулями.
- Кнопки «Регистрация», «Создать личный кабинет», «Регистрация игрока»,
  «Провести турнир» и блок «Участникам» в подвале — **только вид**, `href="#"`.
  Личный кабинет, онлайн-заявки и онлайн-оплата вне объёма договора (§9) и не
  строятся.
- Админ-страницы — временная простая вёрстка на тех же токенах; их дизайн
  отдельным шагом.

## Эксплуатация

- **Один процесс Node.** Не PM2 cluster и не несколько воркеров: `better-sqlite3`
  синхронный, при многопроцессной записи SQLite даёт «database is locked».
- **`NODE_ENV=production`** в проде — иначе cookie уйдёт без `Secure`.
- **За обратным прокси** (nginx/Caddy с TLS) обязательно `TRUST_PROXY=1`. Без
  него `req.ip` вернёт адрес прокси, блокировка по «логин+IP» схлопнется (все
  запросы с одного адреса), а `Secure`-cookie не распознает HTTPS.
- **Миграция — отдельной командой** `npm run migrate` до старта сервера, не
  автоматически при старте (иначе гонка). Схема идемпотентна.
- **Бэкап БД** — не `cp` по живой базе, а корректная выгрузка:
  ```bash
  sqlite3 db/ftso.sqlite ".backup 'backup-$(date +%F).sqlite'"
  ```
  Это та резервная копия, что по договору передаётся заказчику.
- Секреты — в `.env`, в git не попадают. Файл базы — в `.gitignore`.

### Известное ограничение

Ротация `SESSION_SECRET` поддержана массивом, но список секретов читается при
старте — чтобы новый секрет подхватился, процесс нужно перезапустить.

## Что НЕ входит в этот шаг

Наполнение прочих разделов, дизайн внутренних страниц, стилизованные PDF/Excel —
отдельными шагами. Личный кабинет, онлайн-заявки на турниры и онлайн-оплата — вне
объёма договора (§9).
